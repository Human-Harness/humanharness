# Sidekick

Spec: `docs/superpowers/specs/2026-10-25-sidekick-design.md` ("§" below). Plan: `docs/superpowers/plans/2026-10-27-sidekick-part1.md` (slice 1, "Decision N" below) and `docs/superpowers/plans/2026-10-27-sidekick-part2.md` (slices 2–5, "P2 Decision N" below). Spike: `docs/spikes/2026-10-27-sidekick.md` (A1–A7).

## What it is

- A prompt coach. Before the person's prompt goes to the task agent, a free local check looks at it; when something looks off (or the action asks for it, or the person presses Review) a light model reviews it in its own session and a card in the right panel suggests a rewrite. The person sends the suggestion, edits it, or sends as typed. Sidekick suggests and never acts: it has no tools and changes nothing.
- It is core (D1): every harness gets the controller, the top-bar toggle, the panel or its rail, Settings › Sidekick, a Sidekick row in Settings › Models and (once a Sidekick turn ran) a Sidekick line in Settings › Usage.
- It starts **off** unless the manifest says `sidekick: { default: "on" }` (§3). Off, nothing runs: no review, no session, no folder, no usage line (D0, below).
- Part 1 has one sidekick: id `sidekick`, name "Sidekick" (`SIDEKICK_ID`, `SIDEKICK_NAME` in `packages/shell/src/main/sidekick.ts`, Decision 9), and one moment: before you send. Part 2 adds the other moments, learning, several sidekicks, places, presets and import (sections from "Moments" on); with no sidekick records a profile still has exactly that one Sidekick (`DEFAULT_SIDEKICK`).

## The manifest

`sidekick` (`sidekickSchema` in `packages/harness-sdk/src/sidekick.ts`), optional; absent, Sidekick is available, off, with no tips.

- `default`: `on` or `off` (default `off`): the state for a new profile.
- `tips`: domain hints appended to the brief, in English; one text or one per purpose (`sidekickTips`). `humanharness check` warns above `SIDEKICK_TIPS_TOKENS_WARN` (300) tokens (`sidekick-tips` in `packages/cli/src/check.ts`).
- `actions`: the pre-send mode per action id, `auto` (review only when the local check flags), `always` or `off` (`sidekickMode`). Free questions and unlisted actions are `auto`. An unknown action id is a parse error, not a check warning.
- `checks.minWords` (default `SIDEKICK_MIN_WORDS`, 6): below it a prompt with a vague word is flagged even beside something concrete.
- `places` and `presets` (part 2): places a sidekick can be asked about from the harness UI, and ready-made sidekicks offered to the person ("Places and presets" below; the fields are in `docs/architecture/manifest.md`).
- `sidekick` is reserved: an action can't use it as its id (Settings › Models keys Sidekick's model by it, `SIDEKICK_PROCESS`), and `RESERVED_COLLECTIONS` (`packages/harness-sdk/src/data.ts`) holds it.

## The flow

1. **Enter** in the composer, with Sidekick on: `submit` in `packages/ui/src/ChatView.tsx` shows "Reviewing…" with the countdown and calls `client.sidekick.review({ text, force?, attached? })` (IPC `hh:sidekickReview`, `packages/shell/src/main/sidekick-ipc.ts`; a malformed request answers `send`). Plain Enter during a review does nothing. A send `send` would refuse (a turn running, a pre-flight, an open mode or time question: `canSend`) runs no review. `attached` is set when the open scope has material, so "the file" is not missing context.
2. **What is reviewed** (Decision 7): only free text typed in the composer (a new question, a new action's prompt, a follow-up). Choices' follow-ups and harness UI sends are never reviewed. Part 2 also reviews the free text of an input block's answer (`review({ text, block: true })`, below). Slim (interview) mode never shows Sidekick.
3. `SidekickController.review` (`packages/shell/src/main/sidekick.ts`) returns `send` at once when Sidekick is off, pre-send is off, the action's mode is `off`, or the app isn't set up (or the engine's notice isn't accepted).
4. **The local check** (`localCheck` in `packages/workspace/src/sidekick-checks.ts`, 0 tokens): at most one flag per kind, in order `vague`, `missing-context`, `two-asks`, `off-phase`, each with the words and the `[start, end)` span that raised it. The lists are English (§12 Q2). `known` is the scope's note titles plus the data tables the agent sees; a reference that names one of them is not missing context. `off-phase` uses the words (4+ letters, minus a stop list) of the other phases' labels, since phases have no keywords (Decision 4); the open phase comes from `TaskManager.openPhase()`. `attached` mutes `missing-context`.
5. **The decision**: no flag and mode `auto` and no `force` → `send`. The cap reached → `send`.
6. **The model**, within the wait (6 s, 10 s, or "always", which waits up to `SIDEKICK_ALWAYS_MAX_MS`, 60 s; Decision 6): the session for the open task (below), the per-turn prompt `preSendPrompt` (`packages/shell/src/main/sidekick-turns.ts`): `SIDEKICK_PRE_MARK` first, the app, the open phase (its label and its brief's text, one line of at most 600 characters, `PHASE_BRIEF_MAX`; never the brief's file path), the scope's purpose text when a scope record has one, up to 20 note titles, the data tables, the local flags, the UI language by name, the prompt between `<prompt>` tags, and the JSON contract with "Answer with the JSON object only" (A3 was measured with it) and "Omit `rewrite` when the verdict is `send`" (Haiku echoes the prompt otherwise). Never the task's history.
7. `parseReview(reply, prompt)`: the outermost `{…}` checked against `reviewSchema` (zod); a `rewrite` equal to the prompt is dropped; a `suggest` with nothing to show is a `send`. A `suggest` shows a card when `confidence` reaches the speaker's threshold for the card's kind (`thresholdFor`, 0.5 or 0.8, "Learning" below; Decision 5's single 0.5 in part 1); otherwise `send`.
8. **The card** (`SidekickPanel`, `packages/ui/src/sidekick/`): "Before you send": the issues, the suggested prompt as a word diff (`word-diff.ts`), queued prompts ("For later": Put in composer / Drop), and Send suggested / Edit / Send anyway. The flagged spans are underlined behind the composer (`FlaggedText.tsx`, spans clamped to the text, `start > end` skipped). Each new card is announced once in the polite live region. The outcome (`used`, `edited`, `sent-anyway`, or `dismissed` for the cards of the later moments) goes back through `client.sidekick.resolve` so the card leaves, only once Send suggested or Send anyway actually sent (a refused send keeps the card); it is logged in `events.jsonl` ("Learning").
9. **Anything wrong sends the prompt as typed**: a timeout (the notice "timeout"), an engine error, a crash or a reply that isn't the contract (the notice "failed", "couldn't review"), the cap. A late answer is dropped.
10. **Keys.** ⌘⏎ / Ctrl⏎ sends at once, cancelling a running review (`hh:sidekickCancel`), and a card still waiting resolves as `sent-anyway`. ⌥⏎ and the Review button force a review (`force`). The IME guard (`isComposing`, keyCode 229) comes first.
11. **Superseding.** Every review, cancel, turn-off and close bumps a counter (`reviews`); a review overtaken while it waited for its inputs (or its session) ends as `cancelled` and opens nothing. In the renderer a `cancelled` sends as typed (Sidekick turned off mid-review).

The renderer (`useSidekick(client, enabled, refresh)`, `packages/ui/src/sidekick/useSidekick.ts`) reads `client.sidekick.get()` and follows `hh:sidekick` pushes; the refresh key is bumped after a restore (a fresh read beside main's push). The review is skipped under 720 px (`useNarrow`): Enter sends as typed, since a card would have nowhere to show, and a harness side panel shows as `.hh-side` as before. The panel is 330 px, expanded when Sidekick is on at start; the rail is 52 px; both hide under 720 px. With a harness `renderSide`, the expanded head has a Sidekick | Harness switch and the rail sits beside the harness panel (Decision 10). `status` is `off`, `watching`, `reading`, `suggestion` or `capped`. While off, the panel shows a one-time intro card (Turn on / Not now, stored as `introSeen`).

## The session

`SidekickSession` (`packages/runtime/src/sidekick.ts`): a second transport with its own session id, beside the task's.

- **No tools.** `noTools: true` on the transport (`packages/runtime/src/transport.ts`). Claude (`claudeArgs` in `claude-cli.ts`): `--tools ""` (A1: `tools: []`) and `--disallowedTools` with every built-in by name (`ALL_BUILTIN_TOOLS`), the strict empty MCP config (A7), the same `--setting-sources project` as tasks; a no-tools session refuses MCP servers or reference folders. ACP (Codex, OpenCode): no MCP servers, permissions `{ edit: "none", exec: false, web: false }`, the read-only session mode (`acpFields(engine, "none")`); A5 saw no activity or permission request.
- **Turns** run one at a time. `ask` never throws: a crash, an abort or an engine error is a failed answer, with the usage and limits the engine reported. `close()` waits for a running turn, so the controller aborts the turn's signal first. An aborted first turn leaves the session un-started; the next turn reuses the same id.
- **The model** is the `sidekick` process in Settings › Models (`models.tasks.sidekick`), recommended `light` (Decision 13), resolved when the session opens and fixed for it (plan 3c). Settings shows the tier from the saved models, also while off.
- **The working folder** is `<userData>/sidekick/<sha256(resolved base)[0..16]>/<id>/` (`sidekickWorkDir` in `packages/workspace/src/sidekick-brief.ts`; `<id>` is the sidekick's id, `sidekick` for the default one, or a one-off turn's reserved folder: `learn`, `route`, `daily`, `place`, `import`), so per profile, since each profile has its own base. It holds the session's `AGENTS.md` (`sidekickBrief`, in order: the title and intro line with the sidekick's name, "## Personality" when it isn't the default one, "## Rules" (`SIDEKICK_RULES`), its purpose sections, "## Harness tips", then "## About this person" with what it learned; the personality and a custom purpose's text are the person's, so each of their lines is quoted with `> ` and can't open a heading or a list of its own) and the engine's own file, written by `writeSidekickBrief` only when they changed (the cached prefix survives). The brief is written when a session opens and never again for that session (§5).
- **Why outside the base** (Decision 1): the spec puts it at `<base>/.harness/sidekick/<id>/`, but Claude Code loads every `CLAUDE.md` from the working folder up, and Codex reads `AGENTS.md` from the git root down; the base is a git repo with the task's `CLAUDE.md`/`AGENTS.md` at its root. The spike (A2) confirmed the leak, so the folder lives in the app's `userData`. The task's `AGENTS.md` and engine file are never written by Sidekick. Part 2's `events.jsonl` stays in `<base>/.harness/sidekick/`.
- **One session per task** (Decision 14). The controller keys sessions by the open task's id (`runningTask()`). A review with no task open (a new question or action being sent) binds to a "no task" session; the task that starts next adopts it (its pre-task spend stays in the week's total; the task's own lines start its cap). `betweenTasks` (the task manager's hook, called before a task's `current` is set and after it ends) closes every session whose task is no longer open; the no-task session survives exactly one `betweenTasks` after a review used it (the one right before its task starts), so it never outlives the task it was made for. Turning Sidekick off and quitting abort the running review and close every session.
- **Mock mode** (`humanharness dev --mock`): `mockSidekickReply` (`packages/fake-agent/src/mock-claude.ts`) answers prompts starting with `SIDEKICK_PRE_MARK` with a canned JSON from the flags in the prompt: `suggest` (confidence 0.8) for flagged prompts, `send` for a forced review with none (Decision 12). Part 2's turns have their own marks (`SIDEKICK_AFTER_MARK`, `_LEARN_`, `_ROUTE_`, `_PHASE_`, `_DAILY_`, `_APPROVE_`, `_PLACE_`, `_IMPORT_MARK`), and the mock answers each (`MOCK_SIDEKICK_MARKS`, `isMockSidekickTurn`) so none falls through to the recordings: after-reply and learn `{}`, route the first choice, phase change and before-approve `{"missing":[]}`, daily and place a canned line, import a canned draft. The E2E scripts (`packages/e2e/tests/scripts.ts`) answer the same marks.

Latency (spike A4, resumed Haiku turns): p50 4.2 s; 8/9 under 5 s; max 66 s (an API stall). The 6 s wait will run out now and then by design. Codex's cold first turn is about 10 s (adapter spawn and `session/new`), warm turns about 1.3 s.

## Settings

- The reserved `sidekick` collection (§6.4): app-wide, keyed by `id`, `agent: "none"` (`sidekickCollection()`). The settings record is `{ id: "settings", type: "settings", on?, preSend?, afterReply?, headsUps?, wait?, cap?, introSeen?, presetsOffered?, muted?, learnedAt?, lastDaily? }` (`sidekickRecordSchema`: only the settings record has the id `settings`, both ways). Only changed values are stored; back at the defaults, the record is deleted. Defaults (`sidekickSettings`): `on` from the manifest's `default`, `preSend`, `afterReply` and `headsUps` true (P2 Decision 3), `wait` 6, `cap` 20,000, `introSeen` and `presetsOffered` false, `muted` `{}`; `learnedAt` and `lastDaily` are carried through so a toggle never drops them. Part 2's other record types (`learned`, `sidekick`, `scope`) are under "Several sidekicks" and "Learning".
- It lives in its **own** `DataStore` per base (`sidekickStoreFor` in `packages/shell/src/main/index.ts`), never in `dataCollections(h)` (Decision 8): the harness's rules snapshot, the history's data diff and the harness UI's `client.data` never see it. Its file is `<base>/.harness/data/_app/sidekick.json`, beside the others, so it is in the history and undo restores it.
- Writes go through the person's data path: `SidekickStore` (`packages/shell/src/main/sidekick-store.ts`) sends a `put` or `delete` as the person, app-wide, to `personDataRequests`, which finds the store through the optional `storeFor` hook (`PersonDataDeps.storeFor`, `packages/shell/src/main/data-requests.ts`). So a change shares the person-writes queue, its checks and turn-blocked refusals, and is one `Data: sidekick` commit under the open task's trailer. `SidekickStore.set` runs one change at a time, skips a no-op, and never throws (`{ ok: false, message }`). `harnessUiDataRequests` refuses `sidekick` as an unknown collection.
- IPC: `hh:sidekickGet`, `hh:sidekickSet`; the state is pushed on `hh:sidekick` (no `hh:dataChange`). Turning off aborts a running review, clears the card and the notice, and closes every session.
- **After an undo or a profile switch** (`hh:restore`, `hh:restoreTask`, `arrivedInProfile` in `packages/shell/src/main/index.ts`), main calls `SidekickController.refresh()`: it reads the settings again (the undo may have changed them) and the base. Off closes every session, like `set`; another base (a profile switch) drops the running review, the card and the spend of turns not yet logged, and closes the old base's sessions, the loose one too. Then it pushes the state on `hh:sidekick`.
- Settings › Sidekick (`SidekickTab.tsx`, after Models): on/off, pre-send review, the wait, the cap, the tier (a link to Settings › Models) and the week's tokens. Part 2 adds, in order: the after-reply and heads-up checkboxes, "N of M suggestions used" (7 days), "Not flagged" (muted kinds, "<name> · <kind>", with unmute), the presets offer, the sidekicks list with its editor and import, "Sidekicks in this <scope label>", and "What Sidekick learned". The tab is called "Sidekicks" once there are two or more.

## Usage

- Every model turn writes one line in the base's `usage.jsonl` (`sidekickRecord` in `packages/shell/src/main/usage-log.ts`): `phase: "sidekick"` (a `TurnKind`, since `phase` already names the turn kind), `process: "sidekick"`, `moment` (`SidekickUsageMoment`: `pre`, and in part 2 `after`, `learn`, `route`, `phase-change`, `daily`, `before-approve`, `place:<id>`, `import`; heads-ups cost no turn of their own), `sidekick: "<id>"` (the speaker; `route` for a routing turn; learning and import log as `sidekick`), and `task`, `scope`, `action` when a task is open, with the profile, `ok`, `usage` and `limits` when the engine reported them (Decision 2: the spec's `phase: "pre" | "after" | "learn"` would have broken the readers of `phase`). Haiku's thinking tokens are inside `outputTokens` (A6).
- `summarizeUsage` leaves Sidekick lines out of the per-action estimates, task totals and per-scope totals (like material stages), marks a task turn followed by a Sidekick line as unmeasured, and adds `UsageSummary.sidekick` (all four counts) only when there is at least one; with profiles it is the active profile's. Their limit windows still count as the latest window.
- **The cap** (Decision 3): `capTokens` counts input + output + cache writes; cache reads (the cheap repeated prefix, ~16k on Codex) are left out. `sidekickSpent(records, task)` sums only that task's own lines. While no task is open, `state()` adds the tokens of the reviews made so far (`pending`, kept in memory); when a task adopts that session the pending figure is dropped, not moved, so the task's cap starts from its own lines (those pre-task tokens still count in the week's total). At the cap a review sends as typed and the status is `capped`. The panel's foot shows the same number.
- `sidekickWeek` is the last 7 days' tokens for Settings › Sidekick. The controller caches Sidekick's usage lines per base and drops the copy after each line it logs (it assumes one app process per base).

## Moments

Each moment, the controller (`packages/shell/src/main/sidekick.ts`) takes the sidekicks on in the scope with a purpose for that moment, picks one speaker ("Several sidekicks"), and only that speaker calls the model. Every turn starts with its own mark (`SIDEKICK_*_MARK` in `packages/shell/src/main/sidekick-turns.ts`), never sees the task's history, carries the open phase's brief as text (one line, at most `PHASE_BRIEF_MAX`, 600 characters; the `phaseBrief` dep reads the file, so a prompt never holds the brief's path) and the scope's purpose text (`purposeLine`, "Scope purpose: …"), and counts toward the task's cap. Sidekick off: no moment runs and nothing is written (D0).

| Moment | Trigger | Session | Time limit | Result |
|---|---|---|---|---|
| `pre-send` | Enter in the composer, or an input block's free-text answer ("The flow") | the speaker's task session | the wait (6 s, 10 s, "always" up to 60 s) | "Before you send" card |
| `after-reply` | `TaskDeps.turnEnded` after a run turn | the speaker's task session | 60 s (`TURN_MS`) | "After the reply" card |
| `heads-up` | after-reply signals and the review | none for context; the after-reply turn for repeats | — | heads-up card |
| `phase-change` | `TaskDeps.phaseMoved` | the speaker's task session | 60 s (`TURN_MS`) | "Before moving on" card |
| `daily` | the first app start of a local day | one-off, `daily` folder, light | 60 s (`DAILY_MS`) | "Yesterday" card |
| `before-approve` | `client.sidekick.beforeApprove` | the speaker's task session | races the person's wait | `approve`, or a "Before approving" card |
| `place:<id>` | `client.sidekick.ask` | one-off, `place` folder | 30 s (`PLACE_MS`) | free text, no card |

The one-off turns besides those: routing 15 s (`ROUTE_MS`, light, `route` folder), learning 60 s (`LEARN_MS`, `learn` folder), import 60 s (`IMPORT_MS`, standard tier, `import` folder, reading the files included). Each one-off session is closed right after its turn; turning off, a profile switch (`refresh`) or closing aborts it, except import: it is Settings, so turning off doesn't abort it, and `refresh` aborts it only when the base changed (a profile switch). A task-session turn past `TURN_MS` (after-reply, phase change) ends with no card, so a hung CLI never keeps the turn.

- **After the reply** (§4.2, `afterReply`). `TaskManager` calls `turnStarting()` before a run turn and `turnEnded(TurnEnd)` after every task turn, never awaited (`packages/shell/src/main/task-manager.ts`; absent hooks: nothing, D0). Only a `run` turn that ended well, typed by the person, gets a turn: no checkpoint, close or wrap-up prompt, no block answer (`fromBlock`), no mode switch's line (`modeSwitch`), nothing that failed. The setting `afterReply` off, past the cap, no candidate or no engine notice: no turn. A send cancels it (`turnStarting`, and a `sends` counter for one still setting up). The prompt holds the person's prompt and the reply cut by `cutReply` (`SIDEKICK_REPLY_TOKENS`, 1,500; headings beyond the budget become "[… N more headings]"). `afterParts` asks only what the speaker's purposes want: the prompt coach a `gap` and a `next` step, a mentor a `lesson` (≤ 300 characters, "Worth knowing"); only the coach part (any purpose but mentor, custom included) asks for a `repeated` topic, so a mentor-only speaker never names one. A card shows only with a gap, a next step or a lesson; the prompts are kept (the last 5, with their phase) even with the moment off, since a phase change names them. "For later" (queued asks) belongs to `ChatView` and survives only a sent card.
- **Heads-ups** (§4.3), gated by `on`, `headsUps`, the kind not muted and the task still open (settings read again right before the push): the context at ≥ 75 % of the context window (`TurnEnd.context.cap`, the task profile's cap, not Sidekick's token cap), once per task, from `TurnEnd.context` at 0 tokens (it runs with after-reply off) → Finish task; the same ask 3 times (the after-reply turn's `repeated.topic`, trimmed and lower-cased, so it needs after-reply) → Save as decision, which writes a note as the person ("Decision: <topic>", the decision in `decisions`) in the open task's scope with a `Note: …` commit under the task's trailer (`saveDecision`); 2 `off-phase` flags in a row from the review (block answers don't count), naming the other phase → Finish task. Every heads-up has Dismiss. "Finish task" goes through `client.finishTask()`, which refuses while a phase moves or the task isn't waiting.
- **Phase change** (§2a.2, `phaseMoved`). `TaskManager.enterPhase` fires `phaseMoved({ task, from, to })` after a real, applied move by the person, the agent or the app (only made moves, not proposed ones; the move to the close phase too). A process-guard (or a custom purpose with the moment) gets one turn on the phase left (label and brief text), the phase entered and that phase's prompts; `parseGuard` returns what is `missing`, shown as a card (kind `missing`). It never blocks the move; a newer move drops it.
- **Daily** (§2a.2, P2 Decision 12). `daily(now)` runs from `whenReady`, not awaited: once per local calendar day (`lastDaily`, written before the turn so a crash never repeats it), a daily-summary speaker among the sidekicks in the app scope (`APP_SCOPE`) sums up yesterday from `dailyInput`: the titles of yesterday's notes (≤ 20) and the tokens, never their text (`open` is always empty: `TaskManager` can't list open tasks). Nothing yesterday, past the cap, the `daily` kind muted or no such sidekick: no turn. The card survives `betweenTasks`. A sidekick with `defaultOn: false` never speaks at daily, since the app scope has no scope records (an open question, below).
- **Before approve** (§2a.2, P2 Decision 10). `client.sidekick.beforeApprove({ title, text })` (IPC `hh:sidekickBeforeApprove`, title ≤ 200, text ≤ 200,000 characters) gives a process-guard on in the open task's scope one read of the document (`approvePrompt`: cut by `cutReply`, `<document>` tags neutralised) and answers `approve` or a card of what is missing. It never blocks: off, no candidate, the kind muted, past the cap, a failure, a newer check, `client.sidekick.cancelApprove()` or the person's wait running out (a `timeout` event, written in the background) all answer `approve`. **Not wired to any UI yet**: no Approve button exists; the document-review plan must call `beforeApprove` when Approve is pressed and `cancelApprove` when the approval is answered or withdrawn. `cancelApprove` has no id: it aborts whichever check is running.
- **Block answers.** The free text of an input block's answer is reviewed before it is sent (`client.sidekick.review({ text, block: true })`, `InputForm` "Reviewing…", "Send now" and the same countdown as the composer, `ReviewHint`, from the wait setting); choices-only, empty and skipped answers are not. A block card's Send anyway sends the form, Edit focuses the answer's first text or long-text field, Send suggested puts the rewrite in the composer. The hold dies with its form: after an unmount (the question closed, another task) Send anyway sends nothing and the card stays; Skip on a held answer drops the hold and dismisses its card. A card that arrives after Send now, or after a composer review replaced the answer's, is about an answer already sent and leaves as `sent-anyway`. Harness components with input forms of their own aren't reviewed.

The panel draws each kind (`SidekickPanel.tsx`): a speaker line on every card once there are two sidekicks or the speaker isn't the default one (a single default sidekick looks as in part 1); the rail lights for any waiting card with up to 3 marks ("Sidekick · N waiting"); each new waiting card is announced once in the live region.

## Learning

- **Events** (§6.1, `packages/workspace/src/sidekick-events.ts`): `<base>/.harness/sidekick/events.jsonl`, one line per card outcome: `{ at, task?, scope?, action?, sidekick, moment, kind, outcome, confidence? }`. `moment` is the line's own short name (`pre`, `after`, `heads-up`, `before-approve`, `phase-change`, `daily`, `place`; `eventMoment()` maps the SDK's moments), `outcome` is `used`, `edited`, `sent-anyway`, `dismissed`, `muted` or `timeout`. Trimmed to the last 2,000 lines (`SIDEKICK_EVENTS_MAX`; rewritten once 200 past it). `.harness/` is outside the history except notes and data, so the log is never committed and never leaves the machine. Every write goes through the controller's one queue per base (`event()`), since a trim racing an append would lose a line. Off: nothing is appended.
- **Thresholds** per sidekick and kind (§6.2, `thresholdFor`): 0.5; 0.8 when fewer than 20 % of that sidekick's last 10 cards of that kind were used (`used` or `edited`). It needs the full 10 (P2 Decision 4) and `timeout` lines aren't cards.
- **Why shown** (`whyShown`): with at least 3 past cards of that kind from that sidekick, the card says "You took N of your last M <kind> suggestions". Settings shows "N of M suggestions used" over 7 days (`usedShare`).
- **Muting** (§6.3): "Don't flag" on a card adds its kind to `muted[<sidekick id>]` (at most `SIDEKICK_MUTED_MAX`, 20 kinds per sidekick: every flag, after-reply, heads-up, guard and daily kind fits; ≤ 40 characters each; unknown sidekick ids are refused; lookups use `Object.hasOwn`), logs `muted`, and writes a person item "Doesn't want <kind> suggestions from <name>." (not twice). A muted kind is dropped for that sidekick only; muting `off-phase` mutes the flag and the drift heads-up. Settings › "Not flagged" lists them ("<name> · <kind>") with unmute.
- **The learn turn** (§6.4, P2 Decision 6): when a task ends and none is open (a restored task counts), detached from the task flow, with at least 5 events since `learnedAt` (`SIDEKICK_LEARN_MIN`; the prompt names the newest 50). One-off session in the `learn` folder, 60 s. The app writes the result (`writeApp(base, requests)`): all checked first, one `Data: sidekick` commit, refused for another base, while quitting or while a turn blocks writes. Only items with `source: "learned"` change; the person's items (`source: "person"`) are never touched. `learnedAt` moves to the newest event read only after the write succeeded.
- **Learned items** are `learned` records: `{ id: "l-<8 hex>", type: "learned", text (≤ 300), level: "you" | "harness", kind?, source: "learned" | "person", updatedAt }`. They go into a session's brief under "## About this person" when the session opens (never into a place's).
- **"What Sidekick learned"** (`LearnedList.tsx`, Settings): "About you" and "In this app", the person's items marked "Yours", Forget this, Edit (an edited item becomes the person's), Forget everything. It works with Sidekick off. IPC `hh:sidekickLearned`, `hh:sidekickForget`, `hh:sidekickForgetAll`, `hh:sidekickEditLearned`.

## Several sidekicks

- **Records** (§2a, `sidekickRecordSchema`): one ZodObject for the `sidekick` collection with a `type` (`SIDEKICK_RECORD_TYPES`: `settings`, `learned`, `sidekick`, `scope`) and each type's required fields checked in a `superRefine`. A `sidekick` record: `name` (≤ 40), `mark` (≤ 16), `personality` (≤ 1,500), `purposes` (1–6: `prompt-coach`, `focus`, `process-guard`, `mentor`, `daily-summary`, or `custom` with its own text ≤ 600 and 1–7 moments), `order`, optional `tier`, `source` (an import), `preset` and `defaultOn` (absent = on in a scope with no record). A `scope` record: `scope`, `sidekick`, `on`, optional `purposeText` (≤ 600) and `places` (≤ 12).
- **The implicit default** (P2 Decision 2): with no `sidekick` record the store answers `DEFAULT_SIDEKICK` (id `sidekick`, "Sidekick", mark `spark`, prompt-coach and focus), so part 1 profiles need no migration. The first edit, reorder, scope switch or adoption writes it first.
- **Ids** (`saveSidekick`, `packages/shell/src/main/sidekick-store.ts`): the slug of the name (accents stripped), `-2`, `-3` on clashes. Any existing record id is taken, and the ids `learn`, `sidekick`, `settings`, `route`, `daily`, `place` and `import` are reserved (the default sidekick, the settings record and the one-off folders). A slug starting `s-` or `l-` gets a `k-` prefix so it can't collide with scope or learned records. Scope record ids may be hashed (`s-<32 hex>`): always go through `scopeFor(scope, id)`, never build one. Removing a sidekick removes its scope records and muted kinds, and the last one can't be removed; its session closes at the next candidates read, its folder stays on disk.
- **At most `SIDEKICK_MAX`, 20** (`packages/shell/src/main/sidekick-store.ts`): `saveSidekick` counts inside the store's record queue, so a new one past it is refused however quickly saves come (`hh:sidekickSave` and `adoptPreset` both go through it), and `hh:sidekickReorder` takes 1–20 ids.
- **Candidates → speaker** (§2a.3, `packages/shell/src/main/sidekick-route.ts`). `candidates(all, moment, scope, scopeFor)`: in the person's order, the sidekicks with a purpose for the moment, on in the scope (the scope record's `on`, else `defaultOn ?? true`; a failed read counts as on; muting doesn't remove one). `pickSpeaker(list, moment, route, prefer)`: one candidate → it, no turn; `prefer` first (a pre-send flag → the first prompt-coach, a heads-up → the first focus); when every candidate speaks only through custom purposes, one light routing turn picks (`routePrompt`: at most `SIDEKICK_ROUTE_CHOICES`, 10, each cut to 600 characters, context ≤ `SIDEKICK_ROUTE_CONTEXT`, 2,000; skipped past the cap; moment `route`); otherwise, on error, timeout or an unknown answer, the first in order. No candidate: the prompt goes as typed.
- **One session and folder per sidekick** and task, keyed by both, in `<userData>/sidekick/<hash>/<id>/` with its own brief (`sidekickBrief(…, sidekick)`: name, personality, the tips of its own purposes, "## Your purpose") and tier (the record's `tier`, else Settings › Models' `sidekick`). The default sidekick keeps part 1's brief bytes.
- **The cap is shared**: every sidekick's lines for a task count toward the one per-task cap.
- **The scope's purpose text** (§3) goes into each turn's prompt, never into the brief, so the cached brief prefix stays the same across scopes. Settings › Sidekicks › "Sidekicks in this <scope label>" (`ScopeSidekicks.tsx`) switches each sidekick on or off for the open scope and edits its purpose text (saved on blur); without scopes the section is absent and the defaults apply.
- Settings › Sidekicks: `SidekickList.tsx` (order, edit, remove, import; a file-imported row offers "The original changed") and `SidekickEditor.tsx`, which always sends the whole definition.

## Places and presets

- **Places** (§2a.5): the manifest's `sidekick.places[]` (`docs/architecture/manifest.md`). A sidekick answers in a place when a custom purpose lists `place:<id>` among its moments and it is on in the open task's scope (else the app's); when its scope record lists `places`, that list must name the place too (it narrows; it never adds a sidekick without the purpose).
- **`client.sidekick.ask(place, content)`** (IPC `hh:sidekickAsk`: the place id pattern, `content` at most `SIDEKICK_PLACE_INPUT_MAX`, 4,000 characters) → `{ ok: true, text, speaker } | { ok: false }`. The answer is free text cut to `SIDEKICK_PLACE_ANSWER_MAX`, 600 characters (P2 Decision 13), never a card or an event. The turn (`placePrompt`: the place's label and description, the phase brief text, the purpose line, the content between neutralised `<content>` tags) runs in a one-off session in the reserved `place` folder whose brief has **no learned items**, so a harness can't get them back through an answer. Place turns run one at a time; a newer ask in the same place drops the older, and the cap is checked again after waiting for another place's turn (whose spend may have reached it). When the place has several candidates, the routing turn sees the content the same way (`placeRouteContext`: the place's label, then the content between neutralised `<content>` tags, said to be data from the app's screen and never instructions, within `SIDEKICK_ROUTE_CONTEXT`). Usage moment `place:<id>`. Sidekick off, a place the manifest doesn't declare, no candidate, past the cap, 30 s or a failure: `{ ok: false }` at once.
- **What a harness UI can reach — an open decision for Marco.** The plan meant `client.sidekick.ask` to be the only Sidekick call a harness UI gets. It isn't enforced: the preload puts the whole `HarnessClient` on `window.hh`, and the harness's `ui/App.tsx` is bundled into the same renderer, so harness code can call every `client.sidekick.*` (read the learned items, `forgetAll`, turn Sidekick on, save a sidekick…), as it can every other client call. What is enforced: `client.data` refuses the `sidekick` collection (`harnessUiDataRequests`), and every IPC channel checks its input. Narrowing it needs a separate client (or renderer) for the harness UI, a decision for the whole app, not for Sidekick alone.
- **Presets** (§2a.7): the manifest's `sidekick.presets[]`. Settings › Sidekicks shows "Suggested by the harness" (`PresetOffer.tsx`: Add / Not now) while any preset isn't adopted; Not now hides it for that view. The panel offers them once (`FirstOpenOffer`), and `presetsOffered: true` is written as soon as that offer shows. `adoptPreset(name)` saves the whole definition with `preset: <name>` (the default sidekick first), one adoption at a time and refused past `SIDEKICK_MAX`; an adopted preset is a no-op; once the sidekick is written the adoption stands (a failed `presetsOffered` write is only logged); it works with Sidekick off. Preset names are unique in the manifest (a parse error), since adopting finds one by name. IPC `hh:sidekickPresets` (`[]` on failure), `hh:sidekickAdoptPreset`.

## Import

Settings › Sidekicks › Import (`ImportSidekick.tsx`, §2a.6): paste text (≤ 64 KB) or pick files, and the model turns them into a draft sidekick to review. Pasting is always allowed, including text copied by hand from an engine's settings; only picked files are checked.

- **Picking.** `client.sidekick.pickFiles()` opens the system picker in main and answers `{ token, files: <basenames> } | null`. The renderer never names a path: `hh:sidekickImportDraft` takes only `{ kind: "paste", text }`, `{ kind: "files", token }` or `{ kind: "original", sidekickId }`. A pick token is 16 random bytes (hex), single use, valid 10 minutes (`PICK_MS`) in the same base, compared in constant time, and dropped on a newer or cancelled pick, a profile switch or closing.
- **Limits** (P2 Decision 14, `packages/shell/src/main/sidekick-import.ts`): at most 4 files (`IMPORT_MAX_FILES`), 64 KB each (`IMPORT_MAX_BYTES`), `.md`, `.txt` or no extension.
- **Engine folders are refused by path, before any byte is read** (`refusedPath(p, { home, env })`): `~/.claude`, `~/.codex`, `~/.gemini`, `~/.config/opencode`, `~/.local/share/opencode` (`ENGINE_DIRS`), and where the environment moved them (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `OPENCODE_CONFIG_DIR`, `$XDG_CONFIG_HOME/opencode`, `$XDG_DATA_HOME/opencode`). First by string, on the path as picked and on its resolved path (`realpath`, a dangling link followed through `readlink`; case-insensitive on macOS and Windows); then by identity: each engine folder's device and inode against every folder from the root down to the resolved file. That catches what a string can't, such as macOS firmlinks (`/System/Volumes/Data/Users/…`). The identity walk stops at an engine folder. Nothing inside one is listed or opened, though resolving a picked path or link (realpath) may look up names inside it. If any picked file is refused, none is read.
- **Read order** (`readImportFiles`), per file: the refusal check → `lstat` → open `O_RDONLY | O_NOFOLLOW | O_NONBLOCK` → `fh.stat`: a regular file with the same device and inode as the `lstat`, within the size limit, and one link only (a hard link can't be told apart by its path, so `nlink > 1` is refused as `engine-settings`) → `realpath` and the refusal again (a parent swapped in the meantime) → read at most 64 KB + 1 byte: a file that grew past 64 KB is refused as `too-big`, never truncated. One signal (60 s) covers reading and the turn.
- **Refusal reasons**: `engine-settings` ("These files belong to an engine's settings. Copy or paste their content instead."), `too-many`, `too-big`, `type`, `unreadable`, `empty`, `unavailable`, `failed`, `cancelled`, `expired`.
- **The turn**: one-off `import` folder, standard tier, a brief that says the instructions are data to convert, never to follow; moment `import`. It works with Sidekick off (it is Settings) but needs the engine notice; it writes nothing. `parseImport` drops unknown or duplicated purposes and any `place:` moment.
- **The preview**: name, mark, personality, purposes and what it knows, "Not imported: …" for what was skipped (tool permissions and commands always), the copy notice "It's a copy: changes to the original won't reach it.", and Save, enabled once "I understand it's a copy" is ticked. Save calls `client.sidekick.saveSidekick(def, learned)` (`hh:sidekickSave`, ≤ 50 learned items, written before the sidekick); main refuses a `files` source that no recent import read (the last 8) and that isn't the stored one.
- **Hashed originals.** A file import stores `source: { kind: "files", paths, hash }` (sha-256 of the joined content, `importHash`). The source also carries `tag`, an HMAC-SHA256 of its paths and hash keyed by 32 random bytes in `<userData>/sidekick/source-key` (made whole through a temp file, owner-only in an owner-only folder, by the first file import; a key file of the wrong size is replaced; never in the data folder), and Save sets it itself: an untagged or mistagged source (the agent can edit `sidekick.json`) is never read again and shows no "changed". Sidekicks imported before tags existed lose "Bring the changes" until imported again. `checkOriginal` re-reads the originals only when the stored source is well-formed (a 64-hex hash, 1–4 absolute paths) and, for a stored path, only `.md`/`.txt` unless that extensionless path was picked in this session; the refusal applies again. When the hash differs, the row shows "The original changed · Bring the changes", which runs the import again (`{ kind: "original" }`); its Save keeps the id, tier, preset and `defaultOn`.

## Open decisions and known gaps

For Marco (plan defaults are in place):

- The harness UI sees the full client ("Places and presets").
- The routing turn adds a light model call when every candidate is custom-only, beside D11's "only one sidekick calls the model".
- Part 1's prompts changed: the open phase now carries its brief's text instead of the brief's file path (a part 1 bug fixed in part 2).
- A daily-summary sidekick with `defaultOn: false` never speaks at daily.
- `presetsOffered` is written as soon as the panel offer shows, so closing the panel unanswered loses it.
- "Bring the changes" shows a read-only preview without a diff, and overwrites the name, mark and purposes edited after the import.
- A place's candidate needs the custom purpose; the scope record's `places` only narrows (the spec reads as either).
- A block card's Send suggested puts the rewrite in the composer and records `used` before anything is sent.

Known gaps that stay:

- `saveDecision`'s refusals ("This suggestion can't be saved as a decision", "Its task is no longer open") are English messages shown as they are, not translated.
- Only the "Before you send" card has the why line and "Don't flag"; after-reply, heads-up, guard (`missing`) and daily cards have neither, so their kinds (`missing` and `daily` among them) can't be muted from the UI; muting `off-phase` on a pre-send card still mutes the drift heads-up.
- Learned items brought by an import are saved as the person's (`source: "person"`, "Yours"), so the learn turn never changes them.

Not built yet: the Approve button wiring for before-approve (document-review plan); `focus` heads-ups about parallel tasks (the parallel-tasks spec); in the panel, the head naming the last speaker, a row of the scope's sidekicks and turning one off from its mark (§7).
