# Harness authoring — design (plan 4a)

Status: approved in conversation on 2026-10-12. Builds on plan 3 (tasks, notes, choices) and plan 3c (model tiers).

## 1. Why

Every new harness must get three pillars right:
- a decision UI;
- an agentic flow that keeps the AI on course;
- context and model management, so the user gets the best result for the least use of their resources.

Today a developer has to learn the manifest, the briefs, blocks, tiers and compliance rules by reading the demo. Plan 4a gives developers two things in the terminal, where they work:

1. **An agentic guide** that asks the right questions in order and writes the code.
2. **A deterministic CLI** that checks the result, runs a task and opens the app.

## 2. Decisions

- **D1. One repo per harness.**
  - Until the core is published on npm (plan 4b), a harness links to a local core checkout with `link:`.
  - After that, it depends on `@humanharness/cli` by version.
- **D2. The guide writes the code; `check` is the gate.**
  - The guide records each decision in `HARNESS.md` and writes `harness.config.ts`, briefs and blocks directly.
  - `check` validates deterministically.
  - No code is generated by parsing `HARNESS.md`.
- **D3. Minimal template.**
  - `init` copies a small template that runs as is.
  - The demo is a reference example the guide may read, never a starting point to copy.
- **D4. `HARNESS.md` is a living doc.** It is the harness's own decision log (pillar 3 applied to its own development).
- **D5. Everything in English.** Code, docs, `HARNESS.md`, the guide and CLI output are in English. The harness's UI strings stay localized (es/en). The guide talks to the developer in whatever language the developer uses, but writes files in English.

## 3. Package `@humanharness/cli`

New workspace package `packages/cli`, with bin `humanharness`.
- It depends on `harness-sdk`, `engines`, `runtime`, `workspace` and `shell` (the last one for `dev`).
- A harness repo depends only on `@humanharness/cli`.
- The CLI resolves everything else.

| Command | Purpose |
|---|---|
| `init <dir> [--core <path>] [--id <id>]` | Create a harness repo from the template and install the guide |
| `check [--json]` | Validate the harness in the current folder |
| `run <action> [--engine claude\|codex] [--tier light\|standard\|deep] [--folder <dir>] [--language es\|en]` | Run one task against a real engine in the terminal |
| `dev [--engine …]` | Run `check`, then open the app with this harness |

`run` replaces the root script `hh-dev`, and `packages/runtime/src/dev.ts` is removed.

## 4. `init`

1. Refuses a non-empty `<dir>`.
2. Copies `packages/cli/template/` and fills in:
   - `id`, derived from the folder name or `--id`, and validated against the manifest id rule;
   - the name, which starts as the id.
3. Writes `package.json` with `"@humanharness/cli": "link:<core>/packages/cli"`.
   - `<core>` is `--core` or the checkout the CLI runs from, stored as a relative path when possible.
   - Scripts: `check`, `run`, `dev`.
4. Writes `HARNESS.md` from its skeleton (§6).
5. Installs the guide (§5) as:
   - `.claude/skills/new-harness/SKILL.md`, for Claude Code;
   - a "Creating this harness" section in `AGENTS.md`, for Codex.
   Both come from one source file, `packages/cli/guide/new-harness.md`.
6. Runs `corepack pnpm install` and `git init`.
7. Prints the next steps: "open Claude Code or Codex here and run /new-harness".

### 4.1 Template (`packages/cli/template/`)

- `harness.config.ts`:
  - one action, `example`, with a brief at `agent/tasks/example.md`, `tier: "standard"` and `cost: "low"`;
  - `questions: { tier: "light" }`;
  - permissions `{ edit: "none", exec: false, web: false }`;
  - engines `["claude", "codex"]`;
  - languages `["es", "en"]`;
  - every field has a short comment explaining it.
- `agent/AGENTS.md`: the harness's instructions to the AI. It is a placeholder the guide replaces.
- `agent/tasks/example.md`: a brief that ends with `show_choices`.
- One example block (`example-card`) with schema, description and example, plus its UI component.
- `locales/{es,en}.json` with every string the template uses.
- `README.md`, a short one pointing to `HARNESS.md`.

The template passes `check` with no errors and opens with `dev`.

## 5. Guide `/new-harness`

The guide is one markdown playbook, engine-agnostic. It asks one question at a time, records the answer in `HARNESS.md`, then edits the code. It runs these phases in order:

1. **Task.** What job does the user get done, and for whom? It rejects "a chat about X" and asks for the concrete outcome.
2. **Decisions.**
   - It asks which choices the user makes along the way, and what they need to see in order to decide.
   - Each one maps to a block: the core `choices`, or a custom block with a schema.
3. **Flow.**
   - Which actions exist, with a brief per action.
   - Whether a guided `path` applies.
   - What each `choices` option leads to (`followUp`, `action`, `next`).
   - The cost hint for each action.
4. **Context.**
   - What each closed task saves as a note (the `save_note` fields that matter for this harness).
   - Which reference folders, if any.
   - What must never be lost.
5. **Models.**
   - A tier per action and for free questions, with a one-line reason each.
   - `light` for mechanical or short work, `deep` for analysis or design.
6. **Permissions and engines.**
   - The minimal `edit`, `exec` and `web` that the flow needs, each with its reason.
   - Which engines.
7. **Identity.** Name, tagline and logo. No provider brands in names or logos.
8. **Verify.**
   - Run `humanharness check` and fix every error.
   - Discuss the warnings with the developer.
   - Run `humanharness run <action>` for at least one action, and adjust tiers or briefs from the report.
   - Finally, `humanharness dev`.

Rules:
- Each phase ends by updating `HARNESS.md` and the code together.
- The guide may read `<core>/harnesses/demo` as an example, and `<core>/docs/architecture/` for how things work.
- It never edits files outside the harness repo.
- It never reads `~/.claude`, `~/.codex` or `~/.gemini`.
- It suggests running `check` after each phase.

## 6. `HARNESS.md`

The skeleton has these sections:
- **Task**
- **Decisions**
- **Flow**
- **Context**
- **Models**
- **Permissions and engines**
- **Identity**
- **Open questions**
- **Decision log**, with dated entries: decision, reason, alternatives rejected.

The **Flow** section holds one machine-readable table that `check` reads:

```markdown
| Action | Tier | Cost | Purpose |
|---|---|---|---|
| example | standard | low | Shows how an action works |
| (questions) | light | – | Free questions |
```

The **Permissions and engines** section holds one line per permission (`edit: none — reason`, `exec: false — reason`, `web: false — reason`) and `engines: claude, codex`.

Everything else is free prose.

## 7. `check`

`check` loads the manifest with the SDK and reads `HARNESS.md`. Each finding has a rule id, a severity, a message and a file location. Errors give exit code 1. `--json` prints the findings as an array.

**Errors**
- `schema`: the manifest fails the SDK schema (each zod issue is reported).
- `i18n`: a UI string key missing in any declared language, or a label or description without every language.
- `brief-missing`: an action's `prompt` file does not exist or is empty.
- `brand`: a provider or model brand in the harness name, tagline or logo file name. The brand list comes from `engines`: Claude, Anthropic, Codex, OpenAI, GPT, Gemini, Google, Kimi, Moonshot, Qwen.
- `engine-not-allowed`: an engine that is excluded, or pending outside development.
- `harness-md-missing`: `HARNESS.md` is missing or has no Flow table.
- `harness-md-mismatch`: the Flow table and the manifest disagree on action ids or tiers, or the permissions lines disagree with the manifest.

**Warnings (one per pillar, plus resources)**
- `pillar-decisions`: no brief mentions `show_choices` and the harness has no custom block.
- `pillar-flow`: one action, no `path` and no `choices` in briefs, which is effectively a chat.
- `pillar-context`: the harness cannot save notes (for example, every brief tells the AI to skip closing), or `HARNESS.md` → Context is empty.
- `tier-cost`: `cost: "high"` on a `light` action, or `cost: "low"` on a `deep` one.
- `permissions-wide`: `exec` or `web` is enabled, or `edit: "folder"`, with no reason line in `HARNESS.md`.
- `open-questions`: `HARNESS.md` → Open questions is not empty.

## 8. `run`

- It loads the harness and resolves the engine and the profile, with `--tier` overriding the action's tier.
- The work folder is `--folder`, or else a temp folder under the OS temp dir that is printed and kept.
- It drives one task with the same TaskManager logic as the app: brief, index of notes, profile, checkpoint and closing turn. The UI is a terminal adapter.
  - Text streams as plain text.
  - Activities show as one dim line each.
  - Custom blocks print as indented JSON with their name.
  - `choices` print numbered. The developer types a number, free text (a follow-up), or `q` to close the task.
  - Closing runs the `save_note` turn and prints the note path.
- Report at the end:
  - tier, model (requested and reported), effort, cap;
  - per phase (run, follow-up, checkpoint, close): input, output, cache read and cache write tokens;
  - peak context used against the cap;
  - the declared `cost` next to a plain verdict ("used about N tokens; cost hint says low").
  The same data goes to `<folder>/.harness/usage.jsonl` as in the app.
- No credential handling: the engine must already be signed in through its official CLI, or `run` stops with the same message the app shows.

## 9. `dev`

- It runs `check` and stops on errors.
- Then it starts the shell's dev server with `HH_HARNESS_DIR=<harness folder>`, the same mechanism the demo uses, and opens the app.
- `--engine` preselects the engine.

## 10. Testing

- **Unit:**
  - every `check` rule, with good and bad fixtures;
  - `HARNESS.md` Flow table and permissions parsing (extra spaces, missing rows, `(questions)`);
  - the brand list;
  - `--json` output.
- **`init`:**
  - into a temp dir with `--core` pointing at the repo, without running install (a flag for tests);
  - `check` on the untouched template gives zero errors;
  - a non-empty dir is refused;
  - an invalid id is refused.
- **`run`:** a scripted session against the fake agents, piping stdin: pick a choice, then `q`. Assert the printed blocks, the note file and the report fields.
- **E2E:** `init` + `dev` build, then the app opens the template harness and its example action runs with the fake engine.
- **Guide:** a lint test that every phase in `new-harness.md` names the `HARNESS.md` section it fills, and that `SKILL.md` and the `AGENTS.md` section are generated from it unchanged.

## 11. Out of scope

- Release, signing, electron-builder and npm publishing (plan 4b).
- Automatic tier suggestions.
- A harness marketplace or registry.
- Migrating existing harnesses.
- A GUI for authoring.
