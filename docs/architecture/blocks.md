# Blocks

Blocks let the agent show structured pieces of interface instead of loose text.

- A harness declares blocks in its manifest with `defineBlock`. A visible block becomes a `show_<name>` tool and is drawn by the React component the harness registers under that name; a state-only block becomes `update_<name>` and feeds the side panel.
- Every harness also gets two core blocks (`packages/harness-sdk/src/core-blocks.ts`): `choices` (visible, `show_choices`: up to four ways to continue, which move the task along) and `save_note` (hidden, tool `save_note`: the summary that closes a task; the app writes it, never the agent).
- `packages/blocks/src/ui-server.ts` is an MCP server with one tool per block. Its arguments are checked against the block's schema, and valid calls go to the runtime through the bridge (`packages/blocks/src/bridge.ts`): a socket in a private folder, with a random token per runtime.
- The managed section of `AGENTS.md` lists every tool with its description, an example and its JSON schema (`packages/workspace/src/instructions.ts`).
- The runtime turns each forwarded call into a `block` event. The screen draws it with the registered component (`Blocks` in `packages/ui/src/Message.tsx`); `choices` is drawn by the core (`packages/ui/src/ChoicesBlock.tsx`), and a pick goes back to the main process through `client.choose`.
- Calls to our own tools never show as activity: Claude's `mcp__ui__*` and Codex's `ui` server calls are hidden.

## Input blocks

A block may declare `input`, a `z.object` of what the person answers (spec `2026-10-25-input-blocks-design.md`). Everything below applies only to a harness with at least one; any other harness behaves exactly as before (no ids, no `pendingInput`, no `annotate`, no answers section, the same tool answers).

- **Contract** (`packages/harness-sdk/src/block.ts`): `input`, `inputUi` (per field: `kind` text/longText/choice, `label`, `optionsFrom`, `columns`), `submitLabel`, `skippable`, `display(value, language)` and `saveTo: { collection, records? }`. `defineBlock` checks the input is a `z.object`, that the answer settings come with one and that `inputUi` names only input fields; the manifest checks `saveTo.collection` is declared in `data`.
- **Field kinds** (`input.ts`): a string of at most 200 characters is one line, longer or unbounded a growing textarea; a field named `choice` with shown `options` (or any string field with `inputUi.optionsFrom`) and an enum are choices; numbers, booleans, arrays of enums (multi-choice) and arrays of two-string objects (`pairs`) are read from zod. Anything else is `kind: null`: the core form can't draw it and `check` warns (`input-form`) unless `ui/` registers a component. The window gets the result as plain data, `AppState.inputs`.
- **Showing it.** The ui server answers an input block's call with "Done: the person can see it and will answer; wait for their answer.". `TurnController` gives each input block of a task's run turn the id `<task>:<turn>:<index>` (on the `block` event, so the window, the chat log and the task manager share it). `TaskManager` records the last one as `tasks.json` → `current.pendingInput` while the turn runs; a newer one replaces it, closing the task drops it.
- **Answering** (`client.respond(blockId, value)` → `hh:respond` → `TaskManager.respond`). One operation: the block must be the waiting task's pending one (`stale`), the value must pass `input` and stay under 50,000 characters of JSON (`invalid`, with zod's issues by field), a due checkpoint runs first (`stopped` if cancelled, as is a Stop pressed meanwhile), then `saveTo` writes through `DataStore.putMany` as the person in the task's scope (`refused`, with nothing written). Then the question closes, the chat log entry gets `input: { blockId, value, answeredAt }` (`ChatLog.markAnswered`, which rewrites the file atomically and only runs inside this operation, when nothing can append to it), the window gets `{ ok: true, display }`, and the answer goes to the agent as a follow-up: `[answer to <block>]`, the readable line, then a ```json fence with `block`, `blockId` and `value`. Refusals are values, not thrown errors, so their field errors survive Electron's IPC.
- **A stopped or failed send.** When the answer's turn never starts (a Stop, or the send fails before the turn begins), the question is pending again. The chat log keeps its answered mark; the window lets the waiting task's pending question win over that mark and shows the form again, and the next answer overwrites the mark (`markAnswered` writes on the last block with that id).
- **`saveTo`.** Without `records`, the value is the one record; with it, `records(value)` maps the value to records (harness code, like `display`). `putMany` checks every record (permission, schema, key, rules) before saving the file once, so a refusal writes none. Each record's rules see the collection as it stands with the batch's earlier records applied (cumulative), and two records with the same key in one batch are refused (`invalid`). A single-record collection takes at most one. A throw from `records()` or any data refusal is a `refused` result shown to the person; no turn starts. The write has no commit of its own (see `history.md`).
- **The readable line**: the block's `display` (harness code, run in the main process on a copy, logged when slower than 100 ms; a throw, a non-string or an empty string falls back with a log), else one `<label>: <value>` paragraph per answered field.
- **The window**: `Blocks` wraps input blocks in `InputHost` (`packages/ui/src/InputBlock.tsx`), keyed by block id, which keeps the last refusal's errors and a sending state (so the form never flashes "closed" while the answer is on its way). It draws the harness's component with an `input` prop (`InputProps`), or the core view: the question (the shown data's first text), then `InputForm` while pending (disabled while something runs), the answer once sent, or "This question is closed.". Drafts live in memory by block id, past the chat view unmounting and past a stopped send, until the task closes or another question is pending; they don't survive a restart. A harness component that draws the exported `InputForm` must key it by `blockId` (`key={input.blockId}`), since a mounted form reads its draft once.
- **`annotate`** (core, offered only with input blocks): marks quotes of an answered block's text (`ref`: its id or `"last"`, the latest answer before the annotate itself; `field`, else the answer's longest text) as `ok`, `gap`, `wrong` or `note`, each with an optional `comment`. `AnnotateBlock` places each quote at its first free match and lists every mark's note; one not found is listed with its quote.
- **Terminal** (`humanharness run`): an input block's shown data and its fields print as a numbered list; `a` at the prompt answers the pending one field by field (`packages/cli/src/input-prompt.ts`), and a refusal prints its errors (see `authoring.md`).

Known gaps:

- zod's validation messages are in English only; the window shows them as they come.
- `display` and `saveTo.records` can't be stopped, only logged when slow.
- A `saveTo` write that succeeded is not undone when the answer's turn then stops or fails: the question reopens and a second answer writes again. The write is an upsert by key, so derive record keys from the answer (never fresh random keys or timestamps), or a second answer duplicates the records.
- A draft is lost on restart.
