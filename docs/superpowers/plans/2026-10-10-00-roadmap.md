# Human Harness — plan roadmap

Spec: `docs/superpowers/specs/2026-10-10-humanharness-core-design.md`

The spec covers several subsystems. Each plan produces working software that can be tested on its own. Plans 2–4 are written in detail once the previous one lands, because they depend on what the transport spike (task 0 of plan 1) confirms.

| # | Plan | Delivers | Depends on |
|---|---|---|---|
| 1 | **Node foundations** (`2026-10-10-01-foundations.md`) | Monorepo, `harness-sdk`, `engines`, `workspace` (instructions + history), `blocks` (`ui` MCP server + bridge), `runtime` (claude-cli and ACP transports, turn orchestration), `fake-agent`, and a dev CLI that runs one harness turn in the terminal | — |
| 2a | **Desktop app** (`2026-10-10-02a-desktop-app.md`) | `shell` (Electron main/preload/renderer, IPC, per-app config, chat log, engine command resolution for GUI PATH, bundled codex-acp), `i18n` (es/en), `ui` (React kit: setup screen with language/folder/engine, chat, blocks, activity, error cards, history). The demo harness runs as a macOS app with real Claude and Codex | 1 |
| 2b | **Onboarding, usage and app look** (`2026-10-11-02b-onboarding-usage.md`) | Native look (spec `2026-10-11-app-look-design.md`): hiddenInset window, design tokens, Home, Settings sheet (General / Engine / Usage) replacing the setup screen, engine tiles with logo slots, Lexend bundled. Engine detection with `detect.minVersion` (enforced before the first turn), official install (Claude), sign-in / sign-out via `claude auth login` / bundled `codex login` with status checks, test prompt, legal notice + checkbox per engine, `~/.humanharness/engines.json`, usage pill and meter, `usage.jsonl`, manifest `actions` (cost hints, pre-flight warnings), `tagline` and `logo`, new chat on engine switch, `@humanharness/ui/client` | 2a |
| 3 | **Flow and context** (spec `2026-10-12-flow-and-context-design.md`) | Tasks: manifest actions with prompts and an optional guided path, app-driven task state machine, one engine session per task. Core blocks `choices` and `save_note`, notes in `.harness/notes/`, a notes index at the start of each session, read-only reference folders. The demo becomes an architecture explainer for developers (`diagram` and `files` blocks, curated `docs/architecture/`). E2E with Playwright + fake-agent | 2 |
| 3c | **Resources: models and context** (spec `2026-10-12-resources-models-context-design.md`) | Tiers `light`/`standard`/`deep` per action in the manifest. The user can change a task's tier or make it `custom`, and can redefine each tier (model, effort, context cap) per engine in Settings › Modelos. The tier is fixed per task: Claude gets `--model`, `--effort` and `--autocompact`; Codex gets `CODEX_CONFIG`. An unavailable model falls back one tier. At 80% of the cap, a `save_note` checkpoint runs before the engine compacts. Context meter on the task row | 3 |
| 3d | **History and backup** (spec `2026-10-13-history-and-backup-design.md`) | History grouped by task (commit trailers, changed files, "Go back to before this task", plain-language entries). Backup status from the folder's path (synced folder: Drive, iCloud, OneDrive, Dropbox; or a git remote): synced locations offered at first launch, a dismissible notice otherwise, and "Move to …", which moves the folder with its history and rolls back on failure. No cloud or database integrations | 3c |
| 3e | **Mock mode** (spec `2026-10-13-mock-mode-design.md`) | `humanharness dev --mock`: the app with a fake engine replaying hand-editable recordings in `<harness>/mock/<action>.json` (a tree of turns with per-choice branches and an off-script fallback), no tokens, dev only, fresh folders per launch. `run <action> --record` saves a real run in that format; `check` validates it; the demo's recordings drive the e2e tests | 4a |
| 3f | **Setup flow and mock engine** (spec `2026-10-14-setup-flow-design.md`) | Setup as a screen of its own (folder, engine, "All set") instead of the Settings sheet. Home starts only when the app is configured and the engine check passed, otherwise it offers the setup with a card saying what is missing. Settings drops setup (empty states that lead to the flow). Mock mode shows a test engine and a test model, with no notice. Line settings gear | 3e |
| 3b | **Usage tab** (spec `2026-10-14-usage-tab-design.md`) | Settings › Uso measured, with no fixed plans: the windows the engine reports, and per topic how many times it fits in a whole window (or how many more until the reset near the limit), from each topic's last 10 measured tasks in `usage.jsonl`. Engines that report no limits compare each topic's tokens with the average. Each engine declares its primary window and its provider's plans page, linked near the limit | 3 |
| 4a | **Harness authoring** (spec `2026-10-12-harness-authoring-design.md`) | Agentic guide `/new-harness`: an engine-agnostic playbook that walks a developer through task → decisions → flow → context and model tiers → permissions and engines → identity, recording each decision in a living `HARNESS.md`. `humanharness` CLI: `init` (minimal template + guide install, one repo per harness linked to the core), `check` (schema, i18n, per-pillar warnings, compliance, `HARNESS.md` vs. manifest), `run <action>` (one task in the terminal with blocks as text, keyboard choices, notes, token report), `dev`. Minimal template; the demo is a reference example | 3c |
| 5a | **English core** (`2026-10-25-05a-english-core.md`, spec `2026-10-25-language-on-demand-design.md`) | Language is any BCP 47 tag; manifest texts are one English string, with an optional `tone`; `es.json` gone from the core, the demo and the template. Everything the AI reads is English: the managed section tells it to think in English, write to the person in their language and save notes in English. Screens are English until 5b; dates and numbers follow the shown language | 4a |
| 5b | **Translation on demand** (same spec) | Language picker in Settings and the offer after setup; a notice, then a light-tier engine session translates core and harness strings in batches through `save_translation`; validation (keys, placeholders, plural forms), cache with source hashes, retranslation of changed keys only after asking; legal strings under `legal.` always English; pseudo-translation in the fake engine. Written when 5a lands | 5a |
| 4b | **Release** | electron-builder config generated from the manifest, macOS signing and notarization, changesets → npm, Actions (CI per PR, nightly handshake, official harness releases) | 4a |
| 5a | **Scopes and harness data** (`2026-10-25-scopes-and-data.md`, spec `2026-10-25-scopes-and-data-design.md`) | Scopes: a registry in `.harness/scopes.json`, per-scope tasks, notes, notes index, chat, action statuses and usage, a `Scope:` history trailer, the scope picker, and the migration of a flat folder into `main`. Harness data: collections declared in the manifest, stored as JSON under `.harness/data/` and tracked by the history, checked on every write (permission, schema, key, the harness's `rules`), `HarnessClient.data` with `subscribe`, a `data` MCP server for the agent, data tables in a task's first message, and `dataDiff(taskId)`. Harnesses without scopes or data keep working unchanged | master |

Seven more plans follow from the 2026-10-25 specs, in this order: input blocks, harness settings, task modes, task phases, harness setup steps, profiles, material processing. Each is written once the previous one lands.

Additions to the plans above:

- **Plan 2** also owns: the manifest `actions` cost hints, `<folder>/.harness/usage.jsonl` and the usage meter (spec §6 Usage awareness), enforcing Claude `detect.minVersion` at startup, resolving absolute binary paths so the GUI's limited PATH finds the engines, and bundling codex-acp instead of running it through `npx`.
- **Plan 3** covers only the core and the demo harness. Specific harnesses (Socrates, Ariadna, …) are separate developments built on the core, not part of this roadmap; anything they need comes in as generic extension points (manifest actions, blocks, side-panel content).
- **Plan 4** also owns trimming the runtime package's public exports before publishing to npm, copying the engines' logo assets into packaged apps, and swapping the placeholder engine logos for the official ones once the providers' brand guidelines are checked.

Outside this roadmap (separate specs): website and catalog, specific harnesses (Socrates, Ariadna), Windows and Linux, API-key mode. `mcp-kit` (helpers for a harness's own MCP tools) lands with the first harness that needs custom tools — Ariadna — since the demo and Socrates don't.

Chat persistence in `<folder>/.harness/chats/` belongs to plan 2 (the UI owns the conversation view); plan 1's runtime only emits events.

**Legal gate:** blocks no plan. It only blocks publishing signed builds to end users (plan 4, release step). Before that step: an Anthropic Console account and written confirmation from Anthropic.
