The spirit

A chat is the least specific app there is.

Most people don't need a blank prompt. They need help doing one kind of work well. A harness organizes their work first and points the AI at it second. Every harness stands on three pillars.

Pillar 1

A screen for decisions

The interface shows options, criteria and trade-offs, and asks for confirmation at the moments that matter. The person decides; the agent prepares the decision.

Pillar 2

An agentic flow underneath

Phases declared in the harness keep the AI moving toward the same goal the person is working on. Each action runs as a task with its own session, so it never drifts into a different job.

Pillar 3

Care with context and models

Notes in the person's folder keep the key decisions across sessions and engines. Each task gets a light, standard or deep model, so small work never burns the top tier and hard work never lands on a weak one.

The goal: bring the person close to the best result for their task, with close to the best use of their resources.

Principles

What every harness promises its users.

Your own subscription

People sign in to the official tool of the provider they already use. The app installs and configures it. The harness author never holds a key and never pays for anyone's tokens.

Legal before technical

An engine is offered only when its terms allow it. Working is not enough. Each engine records its legal status, the source and the date it was checked.

Your data, in your folder

Everything lives in a visible folder the person picks, with a hidden local history to undo what the agent changed. Nothing leaves the machine except toward the chosen provider. No telemetry.

Know your limits

The app shows where the person stands on their plan before a heavy workflow starts, and records tokens per task so the cost of each step is visible.

Architecture

Built to outlast the models it runs on.

AI changes every few months. How people make decisions about their work doesn't. So the code is split by how fast each part ages: what lasts is built solid, and what ages fast sits behind a seam where a new version can replace it without touching the rest.

Ages slowly · built solid

The human side

  • The decision UI: cards, choices, reviews
  • The harness contract: manifest, phases, blocks
  • The person's data: folder, notes, history, file timeline
  • The task flow: start, choose, finish

Abstracting these would only add weight. They change when the product changes, not when a model ships.

Ages fast · built to swap

The AI side

  • Engines and how we talk to them: CLI today, ACP, native APIs next
  • Which model runs each step
  • How context is managed: notes, checkpoints, cache, native memory
  • Document converters and translation

Each one is a module with a thin interface. Replacing it means writing one new module and naming it in config.

How it stays fast to update

Six rules, checked by a test.

A boundary test reads every package's imports and fails the build when a rule breaks. That is what keeps the seams honest after the first refactor.

  1. Dependencies point down only.An engine never knows about screens; screens never know about engines.
  2. No engine checks outside an engine's folder.Nothing else in the code asks "is this Claude?".
  3. Policies decide and never execute.They return a plan. They don't read files or start processes, so they are cheap to write and test.
  4. Interfaces describe inputs and outputs, not today's mechanism.A new strategy fits the same shape as the old one.
  5. A policy is fixed for the whole task.Switching mid-task would throw away the engine's prompt cache.
  6. Every turn records which policy ran.Variants are compared on real usage, not on a hunch.
A turn, end to end

From a click to an answer in five hops.

A turn is one message from the person and the agent's complete answer. Each hop lives in its own package.

  1. Screen

    The chat or a decision block sends the message through the harness client.

  2. App core

    The task manager decides whether this starts a task or follows one up, and builds the first message.

  3. Runtime

    Saves the folder in the history, then runs the turn through the engine's transport.

  4. Engine

    The official CLI does the work. When it calls a UI tool, the blocks server checks it and forwards it.

  5. Events back

    Text, activity and blocks stream to the window. Tokens go to the usage log. One done closes it.

Harnesses

One core, one app per kind of work.

Each harness is a broad role, not a single feature: a course builder lives inside the teacher, a code review inside the dev. Here is what we are building or exploring, and what making each one takes.

  1. InterviewThe /new-harness guide asks about the task and the decisions the person makes.
  2. FlowActions, phases and a model tier for each step go in the manifest.
  3. ScreensPick blocks from the core and add the views only this role needs.
  4. What it keepsNotes, data collections and settings, declared as schemas.
  5. Try itRun one task against a real engine, check the usage report, open the app.

Build one

A guide that interviews you, then writes the code.

Create a harness from the template and open Claude Code or Codex in its folder. Run /new-harness. The guide asks one question at a time and records each answer in HARNESS.md:

  • the task, and the decisions the person makes
  • the flow and its phases
  • what each task keeps as a note
  • the models, the permissions and the identity

You are responsible for what your harness does with the AI and for the engines you offer.

# create a harness in its own repository
corepack pnpm humanharness init ~/code/my-harness
cd ~/code/my-harness

# shape it with the guide, inside Claude Code or Codex
/new-harness

# validate, run one task, open the app
corepack pnpm check
corepack pnpm run run <action> --engine claude
corepack pnpm dev
